# Refactor review — agent interaction & rendering pipeline (GPUI)

_Scope: 5 file(s). Lenses: state_lifecycle, mutation_authority, concurrency_resources, type_modeling, abstraction_reuse, interfaces_coupling, anti_patterns, effects_purity._

## Summary
The 33 raw findings collapse into a tight cluster around one architectural through-line: **the ACP replay stream is the sole source of truth for the transcript (nothing user-authored is persisted), yet the channel-to-editor pipeline is lossy and asymmetric for everything except agent prose.** Four root causes recur across all eight lenses: (A) `UserMessageChunk` is dropped at the channel boundary so user turns vanish on resume (defect B); (B) the user-turn freeze ritual is copy-pasted across 3–4 sites with no shared authority, so live and replay can never be proven identical; (C) turn-number attribution advances once for an entire replay, collapsing N turns into one `TurnId::Llm(1)`; and (D) auto-scroll keys on row-count delta rather than content growth, hiding the streaming tail (intermittent defect A). The highest-leverage moves are type-level: add a `ReplyEvent::UserMessage` variant (makes the dropped role unrepresentable via match-exhaustiveness) and extract one `freeze_as_user_turn` helper (makes live≡replay true by construction) — these two together close the defect-B class and unblock the turn-attribution fix. A secondary systemic pattern: `TurnId::Llm` is overloaded for system chrome and the block/line partition + list-count parity hold only by incidental coupling between cooperating HashMaps — both are "correct today, fragile to the next edit" hazards a type or `debug_assert` would pin.

## Findings (ranked)

### 1. `UserMessageChunk` is dropped at the channel boundary; `ReplyEvent` has no user-message variant — replayed user turns are unrecoverable (defect B)  ·  state_lifecycle + mutation_authority + concurrency_resources + type_modeling + interfaces_coupling + anti_patterns + effects_purity  ·  effort M  ·  confidence high
- **Location:** `src/acp_channel.rs:979` (explicit no-op match arm), `src/acp_channel.rs:147-176` (`ReplyEvent` enum), `src/bin/yalda-gpui/main.rs:11654-11748` (`apply_reply_events` match has no user arm)
- **Evidence:** `on_receive_notification` forwards `AgentMessageChunk` → `ReplyEvent::Chunk` (acp_channel.rs:939-945) but lumps `SessionUpdate::UserMessageChunk(_)` into the explicit no-op drop arm at line 979, alongside genuinely-additive signals (`AgentThoughtChunk`, `AvailableCommandsUpdate`). `ReplyEvent` (147-176) carries `Chunk`/`ToolCall*`/`Plan`/`Mode`/`Usage`/`Notice` but no user-role payload. On session/load the agent re-emits the entire prior conversation as `SessionUpdate` notifications including `UserMessageChunk`; `reset_for_replay` (main.rs:4925) starts the editor empty and `acp_sessions.json` holds only id/label/active/mode/pane — no transcript. So agent replies reappear while the user's own prompts are dropped permanently. The server-managed path already solved this with a `ServerNotification::UserPrompt` arm (main.rs:11309-11352), proving the direct path is a missing feature, not a design choice.
- **Invariant violated / absent:** INV-1 (replay completeness), INV-6 (reconstruction parity), INV-7 (no transcript persistence dependence): every role visible live must be reconstructible from the replay stream alone. (Note: spec-agent-window.md §200 currently parks `UserMessageChunk` as an "echo" out of v1 scope — resolve this spec/code tension as part of the fix.)
- **Risk:** After every reboot/resume in direct ACP mode the user's prompts are permanently gone; the conversation reads as a one-sided monologue of replies with no questions. Unrecoverable downstream — the channel is the only place visibility is decided, so no later code can recover content decoded away.
- **Refactor move:** Add an unconditional `ReplyEvent::UserMessage(String)` variant. Forward `SessionUpdate::UserMessageChunk(ContentBlock::Text(t))` to it in `on_receive_notification`. In `apply_reply_events`, route it through the shared `freeze_as_user_turn` helper (Finding 2) tagging `TurnId::User(k)`. Suppress the live echo (where Submit already placed the text) via the trimmed-suffix dedupe already at main.rs:11318-11327, or rely on the agent emitting `UserMessageChunk` only on replay. Remove `UserMessageChunk` from the no-op arm so a future drop is a deliberate decision.
- **Why architecturally better:** Makes the user role a first-class, total case of the decode enum rather than an invisible dropped variant. Match-exhaustiveness then forces every consumer (including `apply_reply_events`) to decide what to do with user text — "can this be reconstructed?" becomes a compile-time question instead of a runtime surprise. The channel stops being a lossy boundary for content the master invariant (live≡replay) requires.
- **Migration impact:** n/a
- **Enforcement hook:** New `ReplyEvent::UserMessage` enum variant (type-level; exhaustive match forces the replay consumer to exist) + an in-crate `#[test]` extending the existing `round_trip_with_fake_agent` harness (acp_channel.rs:1394/1452) to replay a `UserMessageChunk` on session/load and assert a `TurnId::User` frozen line lands in the editor. Mark as an INV-1 invariant test.

### 2. The "freeze text as a user turn" ritual is duplicated across 3–4 sites with no shared authority  ·  state_lifecycle + mutation_authority + concurrency_resources + type_modeling + abstraction_reuse + interfaces_coupling + effects_purity + anti_patterns  ·  effort M  ·  confidence high
- **Location:** `src/bin/yalda-gpui/main.rs:12290-12297` (`submit_worksheet`, per-line freeze of non-contiguous editable lines), `12367-12387` (`submit_chatbox`, contiguous range), `11330-11352` (`ServerNotification::UserPrompt`, with extra dedupe at 11318-11327), and the absent direct-ACP replay path (the Finding 1 fix would become a fourth/fifth copy). `src/editor.rs:1286-1317` is the symmetric agent-side primitive (`append_llm_chunk`); no user-side equivalent exists.
- **Evidence:** Each live site independently: normalizes the trailing newline, `programmatic_insert`s the body at EOF, computes start/end lines, calls `add_frozen_lines`, then loops `anchor_for_line` + `metadata_mut::<TurnId>().insert(anchor, TurnId::User(last_seen_turns+1))`. The copies have **already drifted**: the server arm carries a `document_trimmed_end_ends_with` dedupe the chatbox path lacks; newline handling differs three ways (`strip_suffix('\n')` vs `.unwrap_or(&text)` vs `trim_end_matches('\n')`); worksheet freezes line-by-line while chatbox freezes a contiguous range.
- **Invariant violated / absent:** INV-6 (reconstruction parity): there must be one code path (or two proven equivalent) turning "user text + turn number" into frozen, tagged transcript lines, used by both live Submit and replay. Today there are three hand-copied paths and zero shared with replay.
- **Risk:** The Finding 1 replay fix becomes a fourth divergent copy free to drift again (off-by-one newline, line-by-line vs range freeze, dedupe present/absent), so live and replayed user turns cannot be proven to render identically — re-opening defect B in a new form. The dedupe divergence is itself a latent double-insert bug on one path but not the other.
- **Refactor move:** Extract `Editor::freeze_as_user_turn(&mut self, text: &str, turn_k: usize)` (mirror of `append_llm_chunk`) owning newline normalization, EOF insert, `add_frozen_lines`, and per-line `TurnId::User(turn_k)` tagging. Call it from `submit_chatbox`, `ServerNotification::UserPrompt`, and the new replay arm. `submit_worksheet`'s **non-contiguous** per-line freeze is genuinely a different operation — keep it but factor the shared tag-loop, or pass the pre-collected line list; do not force the contiguous-range shape onto it (a naive merge would change worksheet behavior).
- **Why architecturally better:** Collapses four shallow copies into one sharp abstraction whose contract is unit-tested once. "Live and replay produce identical user-turn shape" becomes a single-function equivalence rather than a four-way audit; a caller cannot bypass the invariant by open-coding the wrong helper. Symmetric with the existing agent-side `append_llm_chunk`.
- **Migration impact:** n/a
- **Enforcement hook:** A `#[test]` asserting `freeze_as_user_turn(editor, text, k)` produces frozen ranges + `TurnId::User(k)` tags identical to a simulated live `submit_chatbox` of the same text (the "two paths proven equivalent" check), mirroring the existing `append_llm_chunk` tests at editor.rs:1789-1812. Plus a call-site grep that no path open-codes `add_frozen_lines` + `TurnId::User` tagging.

### 3. Session/load bumps the turn counter exactly once, collapsing an entire replayed conversation into one `TurnId`  ·  state_lifecycle + mutation_authority + concurrency_resources + type_modeling + anti_patterns + effects_purity  ·  effort M  ·  confidence med
- **Location:** `src/acp_channel.rs:1198` (single `turns.fetch_add(1)` on session/load), `src/bin/yalda-gpui/main.rs:11653` (`current_turn = last_seen_turns + 1`, constant per drained batch), `11669` (tag `TurnId::Llm(current_turn)`), `11567` (`last_seen_turns` advanced only on `turn_ended`), `4935` (`reset_for_replay` sets `last_seen_turns = 0`); consumed at `13746-13768` (TurnHeader inserted only on `TurnId` change), `14031-14048` (gutter prints literal `k`).
- **Evidence:** On session/load the worker does one `turns.fetch_add(1)` (with a comment that its only purpose is leaving the cursor on an editable line), then replays the whole prior conversation as notifications. `apply_reply_events` computes `current_turn = last_seen_turns + 1` once per drain and tags every chunk `TurnId::Llm(current_turn)`; `last_seen_turns` stays 0 because it only advances on the single synthetic `turn_ended`. So a 10-exchange history is attributed to turn k=1. TurnHeaders still fire on role change (User vs Llm differ), so normal alternation survives — but the numeric gutter tags (U1/L1/U1/L1…) are wrong for every turn past the first, and **same-role adjacency merges**. Masked today because only agent text replays as one block; Finding 1 activates the full defect.
- **Invariant violated / absent:** INV-3 (turn attribution): the turn counter is the single source of `k` and must advance identically live and on replay so gutter tags and TurnHeaders are correct in both regimes. Constraint 5 (live and replay render identically).
- **Risk:** Even after defect B is fixed, resumed multi-turn transcripts render with flattened/incorrect turn numbering; any future per-turn logic (turn cards, scroll-to-turn, fold/collapse) treats the whole replayed history as one turn. Invisible in single-turn manual testing. Should be fixed in the same change as Finding 1.
- **Refactor move:** Drive turn attribution off the replay stream itself rather than the prompt-response counter (which never fires during replay). Either have the channel emit a turn-boundary `ReplyEvent` between replayed exchanges (the SDK delineates them), or advance `current_turn` on each `UserMessage` boundary during replay so subsequent agent chunks attach to the next `Llm(k)`. Make the `k` source a single function used by both live submit and replay so INV-3 holds by construction. The channel — which observes authoritative notification order — is the right place to assign `k`.
- **Why architecturally better:** Turn number becomes a property of the parsed event sequence (a typed value assigned at the boundary) rather than a side effect of an RPC that doesn't occur on replay. Eliminates the `fetch_add`-once hack whose only stated purpose (cursor placement) is unrelated to attribution.
- **Migration impact:** n/a
- **Enforcement hook:** An in-crate `#[test]` replaying a 2-user/2-agent fake-agent session/load and asserting the editor's `TurnId` metadata sequence is `User(1),Llm(1),User(2),Llm(2)` — not all-1s. Fails today. Mark as an INV-3 invariant test. (Contingent on Finding 1's `UserMessage` boundary signal existing.)

### 4. Auto-scroll tail re-reveal keys on item-COUNT change, not content growth, so intra-line streaming tail falls below the fold (intermittent defect A)  ·  state_lifecycle + mutation_authority + concurrency_resources + type_modeling + abstraction_reuse + interfaces_coupling + effects_purity + anti_patterns  ·  effort S–M  ·  confidence med
- **Location:** `src/bin/yalda-gpui/main.rs:13865-13891` (render-time re-scroll nested inside `if new_count != old_count { … if grew { scroll_to_reveal_item(new_count-1) } }`); pump-side scrolls at `11580-11590` and `11421-11425` (use stale pre-render `list_item_count`). The same follow-decision block (`cursor_at_eof` + `match input_mode { Chatbox => follow_output, Worksheet => cursor_at_eof }`) is byte-duplicated between pump (11580-11590) and render (13880-13890).
- **Evidence:** The authoritative re-scroll runs only when `new_count != old_count` and further only when `grew`. A streamed chunk that extends the last logical line (agent prose before a `\n`) bumps `edit_seq` and the item's wrapped height but adds no `FlatItem`, so `new_count == old_count` and the block is skipped. A streaming fenced code block is the worst case: `detect_block_ranges` folds all post-fence lines into one `(start, lines.len())` range (Finding 12), so the whole block grows as one `FlatItem` with zero count change. The pump scrolls fire every batch but read the pre-render stale count and run before the grown height is laid out, so they reveal the item's old (shorter) bounds. The 13877 comment itself names render as the authority — but render only fires on count change.
- **Invariant violated / absent:** INV-13 (tail visibility under intra-line growth): the auto-scroll trigger must key on "content grew" (`edit_seq` advanced with follow active), not solely on "row count grew."
- **Risk:** Streaming agent text intermittently appears truncated at the tail whenever the final chunk doesn't add a row — the most-cited form of defect A; the content is present, just below the fold. (Caveat: the agent list is `ListAlignment::Bottom` (main.rs:4880), so a bottom-pinned list may already re-anchor on height growth — the user-visible symptom cannot be confirmed from source since GPUI isn't headlessly drivable; one verifier dropped confidence to low on this ground. Hence med overall.)
- **Refactor move:** Split the reconcile (count parity → splice/reset, stays count-keyed) from the follow-scroll. Extract one `follow_tail(c: &AgentState) -> bool` policy and one `reveal_tail_if_following` that both pump and render call. Track `last_scrolled_edit_seq` on `AgentState`; after reconcile, if `follow && edit_seq != last_scrolled_edit_seq && new_count > 0`, call `scroll_to_reveal_item(new_count-1)` regardless of count delta.
- **Why architecturally better:** Ties the scroll trigger to the true cause (content changed) instead of a proxy (row count) correct only when growth happens to add a row. One predicate evaluated against the authoritative post-reconcile count replaces two partial triggers (pump-stale-count + render-grew-only) that each miss the intra-line case, and removes the structural opportunity for the two duplicated copies to drift.
- **Migration impact:** n/a
- **Enforcement hook:** An in-crate `#[test]` over the extracted predicate (`should_follow_tail(follow, content_grew, count)` or the `reveal_tail_if_following` helper): append a chunk with no trailing newline (count unchanged), assert `edit_seq` advanced and the last-item reveal is requested. Today the reveal is skipped. (Asserts the trigger path, not the GPUI visual outcome — a partial hook given headless limits.)

### 5. `append_system_notice` tags system chrome with `TurnId::Llm(k)`, conflating lifecycle notices with agent prose in the attribution type  ·  state_lifecycle + mutation_authority + abstraction_reuse + interfaces_coupling  ·  effort M  ·  confidence high
- **Location:** `src/bin/yalda-gpui/main.rs:11626-11632` (`append_system_notice` → `append_llm_chunk(TurnId::Llm(last_seen_turns+1), …)`), called from the Notice arm (11746) and attach/detach/disconnect/permission/force-restart sites (11360, 11368, 11382, 11496, 11503, 11529, 12230); `TurnId` enum at `4023-4031` has only `Llm`/`User`/`Tool`. TurnHeader logic at 13746-13767 maps `TurnId::Llm` → `TurnRole::Claude`.
- **Evidence:** System notices ("attached: …", "agent disconnected", "permission mode → …", retry `Notice`s) are inserted as frozen lines tagged `TurnId::Llm(current_turn)` via the same `append_llm_chunk` door as real agent prose, and append into the in-flight Llm(k) frozen range. They are durable, role-indistinguishable transcript content. Because they are yalda-local (never replayed as `SessionUpdate`), a live transcript and its resumed reconstruction differ by exactly these lines — and a notice tagged `Llm(k)` landing before any real `Llm(k)` chunk can seed/mis-attribute the turn header and gutter.
- **Invariant violated / absent:** INV-3 (turn attribution) and INV-7/Constraint 5 (live≡replay): a locally-injected, never-replayed `Llm`-tagged line breaks parity and makes "every line tagged `Llm(k)` is agent-authored content of turn k" false.
- **Risk:** Turn numbering and TurnHeaders shift depending on how many notices fired locally, so the same conversation renders differently after resume — live≡replay becomes unprovable. Notices can also perturb `find_llm_insertion_point` (which keys off the last `Llm`-tagged line). A hidden write path to durable role-tagged state that bypasses the intended agent/user write APIs.
- **Refactor move:** Give notices their own representation — a `TurnId::System` variant (or a `FlatItem::SystemNotice(String)` the view model emits directly) — excluded from agent-turn numbering and never emitting a Claude TurnHeader. Keep `append_llm_chunk` strictly for agent-authored content. Define the replay-parity contract over `{User, Llm, Tool}` only, with notices an explicitly non-persisted, non-attributed lane.
- **Why architecturally better:** Separates "agent said this" from "yalda is telling you about the connection" at the type level, making the masquerading-as-turn-k state unrepresentable. The replay-parity invariant becomes stateable and testable precisely (parity over agent+user turns, notices excluded by construction) instead of silently false.
- **Migration impact:** n/a
- **Enforcement hook:** Add `TurnId::System` (or `FlatItem::SystemNotice`) — match-exhaustiveness then forces every `TurnId` match (13761-13764, 14031-14051, the 4046 card-bg, etc.) to decide how System renders, with no silent `Llm` conflation. Plus a `#[test]` asserting injecting N notices does not change the `TurnId::Llm(k)` assigned to the next agent chunk (INV-3), and that the Finding 1/3 parity test can filter System lines.

### 6. `TurnRole` is recomputed via an `unreachable!()` partial mapping instead of a total `Option`-returning function  ·  type_modeling  ·  effort S  ·  confidence high
- **Location:** `src/bin/yalda-gpui/main.rs:13751-13765` (`dominated_by` narrows `TurnId::Tool(_) => None`, then the role match re-matches `dt` with `TurnId::Tool(_) => unreachable!()`)
- **Evidence:** The code first narrows `dominated_by = match tid { TurnId::Tool(_) => None, other => Some(other) }`, then later matches `dt` again with `TurnId::Tool(_) => unreachable!()`. The exhaustiveness checker can't see the Tool case was already excluded, so a panic arm papers over a partial function. The domain rule "a header-owning turn is `Llm` or `User`, never `Tool`" lives in a runtime `unreachable`.
- **Invariant violated / absent:** Implicit: header-owning turns are exactly `{Llm, User}`; `Tool` turns anchor ToolGroups and never emit a TurnHeader — currently expressed as an unreachable branch, not a type.
- **Risk:** If `TurnId` gains a variant or the narrowing is refactored, the `unreachable` becomes a live panic in the paint path — a crash instead of a compile error.
- **Refactor move:** Introduce `enum HeaderRole { Claude, User }` and a total `fn header_role(TurnId) -> Option<HeaderRole>` (`Tool -> None`). Build the header from the `Option`, deleting the `unreachable`. The two-step narrow collapses into one total function.
- **Why architecturally better:** Turns a partial function with a panic into a total function over the enum; "Tool has no header" becomes a returned `None` checked by the compiler rather than an `unreachable` that can rot into a crash.
- **Migration impact:** n/a
- **Enforcement hook:** The total `header_role` function returning `Option<HeaderRole>` (no `unreachable`), compiler-exhaustiveness-checked; plus a unit test asserting `Tool -> None` and `Llm/User -> Some`.

- **Location:** `src/bin/yalda-gpui/main.rs:11674` (`tc.tool_call_id.0.to_string()`), `11694`, `11721`, `13698-13703` (`tool_call_order: Vec<String>`, `tool_call_anchor_line`/`tool_calls` keyed by `String`), `FlatItem::ToolGroup { ids: Vec<String> }` (enum near 2652)

- **Migration impact:** n/a

### 8. `list_item_count` parity with `flat_items.len()` is maintained by hand-rolled per-surface reconciles rather than one encapsulated mutator  ·  type_modeling  ·  effort M  ·  confidence high
- **Location:** `src/bin/yalda-gpui/main.rs:13865-13874` (render_agent reconcile), `12917-12919` / `13252-13256` / `13369-13371` (doc + two edit-view parallel reconciles), `3858`/`3910` (`Cell<usize>` mirror), `4512`/`4622` (field copies)
- **Evidence:** The `ListState` item count is mirrored into a separate scalar (`c.list_item_count`) updated only inside `if new_count != old_count`. Parity with `flat_items_arc.len()` holds only if every early-return path also updates it and no path mutates the `ListState` out of band. The same `new_count != count` pattern is hand-rolled in at least four render surfaces, each its own block. Nothing type-level ties "the `ListState` GPUI will paint" to "the flat-item count we built."
- **Invariant violated / absent:** INV-12 (count parity): `list_item_count == flat_items.len()` after every render; a `ListState` count below the flat-item count never paints the trailing items (a direct cause of tail cut-off).
- **Risk:** A missed update on any branch (early return after building flat_items, or a future surface) leaves `ListState` short and silently truncates the tail. The invariant is enforced by discipline at N call sites, not one.
- **Refactor move:** Encapsulate the `(ListState, count)` pair in a small type (e.g. `ReconciledList`) with one `reconcile(&mut self, new_len) -> Grew` method that updates both atomically and returns whether it grew; make `list_item_count` private to it. All surfaces call `reconcile`; no surface can set one without the other.
- **Why architecturally better:** Makes "count out of sync with `ListState`" unrepresentable by colocating the two fields behind one mutator — the parity invariant moves from four comment-guarded sites into one type's single method.
- **Migration impact:** n/a
- **Enforcement hook:** The `ReconciledList` wrapper whose only mutator updates both fields, plus a `debug_assert!(self.count == flat_items.len())` at the end of `render_agent`.

### 9. The agent turn lifecycle is a cluster of loose booleans/`Option<Instant>` fields rather than one state enum, allowing impossible combinations  ·  state_lifecycle  ·  effort L  ·  confidence med
- **Location:** `src/bin/yalda-gpui/main.rs:4629-4647` (`awaiting_reply: bool`, `turn_started`/`last_event_at`/`stop_requested_at: Option<Instant>`, `last_seen_turns`), reset across `pump_session` (11567-11571), `submit` (12318-12322), the server path (11302-11305), `reset_for_replay` (4931-4935)
- **Evidence:** A turn's state (Idle / Awaiting / Streaming / StopRequested-graceful / StopRequested-escalated / replaying) is spread over four loosely-coupled fields whose valid combinations are unwritten convention. `stop_requested_at`'s own doc (4639) describes the `(stop_requested_at, awaiting_reply)` pair as a 2-field state machine (a second Stop "while this is set and still awaiting" escalates). Nothing prevents `awaiting_reply=false` with `stop_requested_at=Some`, or `turn_started=Some` with `awaiting_reply=false`; every transition site must reset all four in lockstep by hand.
- **Invariant violated / absent:** Lifecycle states should be explicit types with constrained transitions so impossible states are unrepresentable; cancellation/replay/terminal states should be modeled, not implied by loose flag combinations.
- **Risk:** A missed reset at any of ~5 transition sites strands the turn in a contradictory state (spinner shows "awaiting" forever, or a stale `stop_requested` escalates the next turn to a hard kill). The Stop-escalation logic is especially fragile because it depends on a two-field invariant no type enforces. (Med: the bad combinations are shown reachable by convention/structure, not a demonstrated live path — the win is provable-correctness-by-construction.)
- **Refactor move:** Introduce `enum TurnPhase { Idle, Awaiting { started, last_event }, StopRequested { since, escalated: bool }, … }` on `AgentState`, replacing the four fields. Transition functions (submit, on_event, finalize, reset_for_replay) become total over the enum; the thinking-indicator and Stop-escalation read the variant instead of probing flag combinations.
- **Why architecturally better:** Makes contradictory combinations unrepresentable and centralizes transitions, so the per-tick pump and the Stop handler are total functions over a single state rather than coordinated multi-field mutations. Cancellation and replay become named variants instead of inferred from `Option` emptiness.
- **Migration impact:** n/a
- **Enforcement hook:** The `TurnPhase` enum itself excludes the bad combinations; a `#[test]` over the transition functions (submit → stop → stop → finalize) pins the escalation behavior currently documented only in a field comment.

### 10. The block/line partition holds only by incidental coupling between `block_ranges` and `block_cache`; a detected-but-unparsed range could silently vanish its lines  ·  type_modeling + effects_purity  ·  effort M  ·  confidence med (correctness-hardening)
- **Location:** `src/bin/yalda-gpui/main.rs:3287-3290` (fence range emitted), `3319-3334` (`parse_block_range` returns `None` if the first block isn't Table/CodeBlock), `13710-13739` (cache built only from `Some` parses; `in_block` populated from `block_ranges ∩ block_cache`, with `block_ranges` cloned at 13727 as the "obvious" source)
- **Evidence:** When `frozen_line_count` changes, `new_cache` gets an entry only when `parse_block_range` yields `Some`. `in_block` is then populated by iterating `block_ranges` and looking up `block_cache.get(...)` — so a range `detect_block_ranges` emitted but `parse_block_range` couldn't parse is absent from `block_cache`, hence not added to `in_block`, and its lines fall back to standalone Lines. The partition is correct **today** — but only because `in_block` keys off `block_cache` rather than off `block_ranges` (the more natural source, which is what's cloned at 13727). A future edit building `in_block` from `block_ranges` would drop every line of an unparseable block.
- **Invariant violated / absent:** INV-10 (block/line partition): every editor line is rendered exactly once — as the Block owning its range or as a standalone Line. Today upheld by an implicit two-map coupling and a comment, not by construction.
- **Risk:** A latent trap: the partition is correct by accident of which map `in_block` is built from. Any refactor treating `block_ranges` as the source drops content lines with no test catching it — the structural form of defect A.
- **Refactor move:** Make the fallback explicit and total: have parse return an enum (`Parsed(RenderedBlock) | FallBackToLines`) instead of `Option`, and have the flat-item builder consume detect+parse as a single partition pass that emits either one Block or the constituent Lines for every detected range. Then `in_block` cannot disagree with what was emitted because both come from one pass.
- **Why architecturally better:** Replaces "two HashMaps must agree" with one total function whose return type makes "suppressed but not emitted" unrepresentable. "Rendered exactly once" becomes a property of the type, not of which HashMap a later reader indexed.
- **Migration impact:** n/a
- **Enforcement hook:** A `#[test]` feeding a frozen range `parse_block_range` rejects (e.g. a 3-line `|`-delimited block that isn't a valid table) and asserting `flat_items` contains a Line for every source line of that range (count parity over the range), plus a `debug_assert` in the flat build. The `Result`-shaped parse return is the type hook.

### 11. The view-model memo fingerprint omits an input the flat build reads (resolved tool anchor lines), so memo soundness rests on an unstated `edit_seq` co-variation invariant  ·  interfaces_coupling  ·  effort S  ·  confidence med (correctness-hardening)
- **Location:** `src/bin/yalda-gpui/main.rs:4762-4780` (`view_model_fingerprint`), `13696-13703` (`tools_at_line` resolved via `c.editor.line_for_anchor(anchor)` inside the build)
- **Evidence:** The fingerprint hashes `edit_seq`, `frozen_line_count`, `tool_call_order.{len,last}`, the expanded set, and `awaiting_reply`. But the flat build also resolves `tool_call_anchor_line` → current line via `line_for_anchor(anchor)` (13700), which can change when frozen content above shifts. That shift bumps `edit_seq` today, so the memo is sound by transitivity — but the fingerprint never names the dependency, so it's sound only by an unstated invariant ("every input to anchor resolution also bumps `edit_seq`").
- **Invariant violated / absent:** INV-8 (memo soundness): the fingerprint must change whenever any input to the flat build changes; new inputs must be added or rows go stale ("cut off").
- **Risk:** A future change moving a tool anchor or altering blank-collapse inputs without bumping `edit_seq` would silently serve stale `flat_items` (defect A, the "cut off" class), and nothing flags it because the dependency is implicit — the memo key knows less than the build it guards.
- **Refactor move:** Either document and `debug_assert` that anchor-line resolution depends only on `edit_seq` (re-resolving anchors at a fixed `edit_seq` is idempotent), or fold a cheap hash of the resolved tool anchor lines into the fingerprint so the key names every input it depends on.
- **Why architecturally better:** The memo key becomes a truthful summary of the build's inputs, so "fingerprint unchanged ⇒ output unchanged" is provable from the key alone rather than from a global `edit_seq` assumption a future edit can break.
- **Migration impact:** n/a
- **Enforcement hook:** A `#[test]` that mutates each build input in isolation and asserts the fingerprint changes (an executable INV-8). Today it passes for tool anchors only because `edit_seq` moves — asserting against the *named* inputs surfaces the gap.

### 12. Streaming/unterminated code fence is collapsed into one block range spanning to EOF, amplifying the count-keyed scroll defect and re-parsing the whole block per chunk  ·  mutation_authority  ·  effort S  ·  confidence med (behavior-changing)
- **Location:** `src/bin/yalda-gpui/main.rs:3275-3290` (fence range pushed `(start, lines.len())` even when no closing fence is found, because the inner `while i < lines.len()` exhausts and `i > start + 1` is still satisfied)
- **Evidence:** For an open fence with no closing ```` ``` ````, the inner loop runs to `i == lines.len()` without breaking, then `if i > start + 1` holds, so `ranges.push((start, lines.len()))` — the whole tail becomes one block. The 3286 comment ("Only emit if we found a closing fence") is misleading: exhausting the loop also satisfies the guard. As lines stream in, the range is re-detected as `(start, new_len)` and `parse_block_range` re-joins+re-renders the entire growing block each freeze (O(block) per chunk). Because all growth folds into one Block `FlatItem`, `flat_items.len()` doesn't change, so the INV-13 count-keyed re-scroll (Finding 4) is skipped for the whole streaming duration.
- **Invariant violated / absent:** INV-11 (mid-stream stability): an opened-but-unclosed fence must render its arrived lines without unstable layout; the all-to-EOF capture interacts pathologically with INV-13.
- **Risk:** Long streamed code blocks (very common in agent replies) are the worst case for tail truncation: the block grows for many chunks with zero count change, so the tail is never re-revealed until the turn ends. Plus O(block) re-render per chunk.
- **Refactor move:** Preferably land the Finding 4 content-growth scroll fix, which makes the block-vs-lines choice scroll-correct either way. Alternatively (behavior-changing): do not emit a range for an unterminated fence (require a matched closing fence, symmetric to the ≥3-row table rule) so in-progress lines render as plain Lines until closed — each new line is then its own `FlatItem` and the count-keyed path works as a stopgap.
- **Why architecturally better:** Makes block detection a function of completed structure, not of a half-arrived delimiter, so the detected partition for a given frozen-line count is stable and predictable; removes a per-chunk full-block re-parse.
- **Migration impact:** n/a
- **Enforcement hook:** A `#[test]` feeding `detect_block_ranges` a frozen buffer with an unterminated ```` ``` ```` and asserting either no range is returned (option a) or, combined with Finding 4, that a follow-reveal still fires as the fence grows. (Note: option a is **not** behavior-preserving — it changes how in-progress fences render — so prefer it only alongside Finding 4.)

### 13. The per-tick drain budget (64) can finalize a turn mid-replay when the queue momentarily empties and the post-load counter is already bumped  ·  effects_purity  ·  effort L  ·  confidence med (behavior-changing)
- **Location:** `src/bin/yalda-gpui/main.rs:11443` (`PUMP_EVENT_BUDGET=64`), `11540-11554` (budget loop sets `more_pending`), `11554-11572` (`turn_ended = !more_pending && current_turns > last_seen_turns`; tail drain + finalize only when `turn_ended`); coupled to `acp_channel.rs:1198` (single post-load `fetch_add`, Finding 3)
- **Evidence:** The drain caps at 64 events/tick; `more_pending` gates `turn_ended`. On session/load replay of hundreds of notifications, multiple ticks are needed, and eventual-full-drain relies on the caller re-invoking `pump_session` (its bool return drives the loop). But because session/load already bumped `current_turns` (Finding 3), if a tick drains the queue to empty between notification bursts, `more_pending=false` and `turn_ended` fires — running `finalize_agent_turn` (trailing newline / clearing the llm-tail cache) *in the middle of* the replay, re-anchoring subsequent replayed chunks incorrectly.
- **Invariant violated / absent:** INV-4 (drain completeness): a per-tick budget that silently leaves events queued is acceptable only if the loop guarantees eventual full drain — and turn-end must not be inferred from a transient empty queue.
- **Risk:** Intermittent, ordering-dependent premature finalize mid-replay on freshly-resumed sessions — hard to reproduce, consistent with defect A's tail anomalies on resume. Conflates the DECISION "is the turn over" with the effect-proxy "is the queue empty right now."
- **Refactor move:** Make the replay regime explicit: gate `finalize_agent_turn` on a real end-of-replay signal (a typed `ReplyEvent` or a "replay complete" flag from the channel) rather than "queue momentarily empty + turn counter advanced." Until replay is known-complete, keep draining without treating an empty queue as turn-end. Separates the decision (finalize?) from the timing proxy.
- **Why architecturally better:** Turn-end becomes a fact carried in the event stream, not inferred from drain timing — removing a race where a transient empty queue plus a pre-incremented counter finalizes a turn mid-replay. The core decision becomes testable without timing.
- **Migration impact:** n/a
- **Enforcement hook:** A `#[test]` with a fake agent replaying >64 chunks in bursts, asserting `finalize_agent_turn` runs exactly once, after the last replayed chunk (no mid-replay finalize). The explicit replay-complete signal is the type hook. (Coupled to the Finding 3 fix.)
