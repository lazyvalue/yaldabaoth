Menu & File Browser — Approaches

Three approaches to implementing the which-key menu system + file browser

A

Menu-First (Recommended)

Build the which-key popup system first as a generic, reusable overlay. Then build the file browser as the first "command" that gets summoned through it. The menu system becomes the foundation for all future commands.

Pros

  • Menu system is reusable for all future commands
  • Clean separation: menu dispatches, commands execute
  • File browser is just one consumer of the menu API

Cons

  • More upfront abstraction before visible payoff
  • Menu system needs to be designed generically enough
B

File Browser First

Build the file browser side panel directly, wired to a simple Space → f shortcut. Extract the menu system later when you add more commands.

Pros

  • Fastest path to a working file browser
  • Less abstraction upfront

Cons

  • Menu system is an afterthought — may not compose well
  • Refactoring later to add the popup
C

Parallel Build

Build both the menu popup and file browser in parallel as independent modules, then wire them together at the end.

Pros

  • Both features progress simultaneously
  • Clear module boundaries from the start

Cons

  • Integration risk — may not fit together cleanly
  • More context switching during development
